# 滑窗时序数据加载性能优化计划

## 目标与约束
- 在不改变训练/评估语义与结果口径的前提下，降低滑窗数据组织的内存占用与数据加载耗时。
- 优先改造 `easytsf/runner/data_runner.py`、`train.py` 与各 Runner 的批处理转换逻辑，保持对现有配置兼容。
- 优化覆盖训练、验证、测试三条数据链路，并兼容当前 Lightning + Ray Tune 入口。

## 现状与主要瓶颈
1. `DataInterface` 初始化阶段一次性加载数组并构造时间特征，启动时延集中。
2. `train/val/test_dataloader()` 内部对切分数组执行 `.copy()`，导致额外内存峰值与拷贝时间。
3. `train.py` 通过 `len(data_module.train_dataloader())` 额外触发一次 train dataloader 构建。
4. 多个 Runner 在每个 batch 执行 `float()` 转换，存在重复类型转换开销。
5. DataLoader 未显式配置 `pin_memory/persistent_workers/prefetch_factor`，吞吐未充分优化。

## 实施步骤

### 阶段 1：零语义变更的快速优化
1. 去除三类 dataloader 中不必要的 `.copy()`，改为切片视图传入 `GeneralTSFDataset`。
2. 在 `DataInterface` 内缓存 `train/val/test` 的 `Dataset` 与 `DataLoader` 实例，避免重复构建。
3. 调整 `train.py` 的 `steps_per_epoch` 计算方式：复用已缓存的 train loader，避免二次初始化。
4. 在 DataLoader 增加可配置参数并给出默认策略：
   - `pin_memory`（GPU 训练默认启用）
   - `persistent_workers`（`num_workers > 0` 时启用）
   - `prefetch_factor`（仅 `num_workers > 0` 时生效）
5. 将时间特征构造中的 Python 循环替换为 NumPy 向量化实现，减少 CPU 侧开销。

### 阶段 2：滑窗访问与类型转换优化
1. 为 `GeneralTSFDataset` 增加可选“索引预计算”模式：
   - 仅预计算窗口起点索引数组（`int32`），不预生成完整窗口数据。
   - 默认按需切片，数据量大时可通过配置切换索引预计算。
2. 统一输入 dtype 策略：
   - 在数据模块输出阶段尽量保证 `float32`。
   - Runner 移除不必要的每步 `float()`，改为“仅在 dtype 不匹配时转换”。
3. 检查模型中可能触发 CPU/GPU 隐式拷贝的类型写法，改为设备无关转换方式。

### 阶段 3：按规模启用的进阶方案（可选）
1. 增加 `np.load(..., mmap_mode='r')` 可配置开关，用于超大数据集降低内存峰值。
2. 为时间特征提供延迟计算/按需禁用策略，减少无效特征构建。
3. 为训练链路增加基于数据规模的自动建议（如 `num_workers`、`batch_size`、`prefetch_factor` 组合）。

## 配置设计
在 `config/base_conf/task.py` 新增并保持向后兼容：
- `pin_memory`（bool，默认按设备类型自动）
- `persistent_workers`（bool，默认 `num_workers > 0`）
- `prefetch_factor`（int，默认 2，仅多进程生效）
- `use_mmap`（bool，默认 false）
- `precompute_window_index`（bool，默认 false）

## 验证方案
1. 正确性验证
   - 训练/验证/测试全链路可运行；
   - 关键指标与改造前在容忍范围内一致；
   - Ray Tune 入口可正常启动试验。
2. 性能验证
   - 采集首轮启动时延、每 epoch 数据加载耗时、峰值内存；
   - 对比优化前后，输出收益表（单卡与多进程各一组）。
3. 稳定性验证
   - `num_workers=0` 与 `num_workers>0` 两种模式均通过；
   - Windows 环境下多进程数据加载无异常退出。

## 风险与回退
1. 风险：去除 `.copy()` 可能暴露上游原地写入副作用。  
   - 缓解：排查训练链路是否有原地改写输入；必要时仅在发现写入路径处局部拷贝。
2. 风险：`persistent_workers` 在部分环境可能引发 worker 生命周期问题。  
   - 缓解：通过配置可关闭，默认按 `num_workers` 安全启用。
3. 风险：`mmap` 在网络磁盘场景可能出现 IO 抖动。  
   - 缓解：默认关闭，按数据规模与存储介质手动开启。

## 交付顺序
1. 先完成阶段 1 并给出基线对比结果。
2. 再完成阶段 2（索引与 dtype 优化），复测收益与稳定性。
3. 最后评估阶段 3 是否纳入默认方案，或作为可选高阶能力保留。
